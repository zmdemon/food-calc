# Паспорт проекта «Рацион»

## 1. Назначение

«Рацион» — локальное одностраничное приложение для составления типичного дневного рациона. Пользователь ведёт собственный каталог продуктов, выбирает из него продукты на день, задаёт количество в граммах и получает автоматический расчёт пищевой ценности и стоимости.

Приложение рассчитано на личное использование. Это информационный калькулятор, а не медицинская система и не источник персональных диетологических рекомендаций.

## 2. Основной сценарий

1. Пользователь создаёт или импортирует продукты в каталог.
2. Из каталога он добавляет нужные продукты в типичный дневной рацион.
3. Для каждой позиции указывает количество в граммах.
4. Приложение рассчитывает дневные БЖУ, клетчатку, калории и стоимость.
5. Дневная стоимость пересчитывается на условный месяц из 30 дней.
6. Пользователь может задать собственные дневные цели для БЖУ и клетчатки.
7. Отдельные позиции можно временно исключить из расчётов, не удаляя их из рациона.
8. Активный рацион можно скопировать в виде чистого Markdown-отчёта для передачи человеку или чат-боту.

Без авторизации данные хранятся только в браузере. После входа через Google приложение сохраняет отдельную локальную копию аккаунта и безопасно синхронизирует её с персональным документом пользователя в Cloud Firestore.

## 5. Модель данных

### 5.1. Продукт

```ts
type Product = {
  id: string
  name: string
  protein: number
  fat: number
  carbs: number
  fiber: number
  calories: number
  packagePrice: number
  packageWeight: number
}
```

`protein`, `fat`, `carbs`, `fiber` и `calories` задаются на 100 г продукта. Цена относится ко всей упаковке, вес упаковки задаётся в граммах.

`id` генерируется приложением через `crypto.randomUUID()`. При ручном создании или обычном импорте продуктов пользователь его не передаёт.

### 5.2. Дневной рацион

```ts
type RationEntry = {
  id: string
  productId: string
  amount: number
  enabled: boolean
}
```

Каждая позиция рациона имеет собственный `id`, поэтому один продукт может быть добавлен несколько раз. `productId` связывает позицию с каталогом, `amount` хранит граммовку, а `enabled` управляет участием в расчётах. Порядок элементов массива является пользовательским порядком строк и меняется drag-and-drop.

### 5.3. Дневные цели

```ts
type NutritionTargets = {
  protein: number
  fat: number
  carbs: number
  fiber: number
}
```

Цели устанавливаются пользователем вручную. Значение `0` означает, что цель отключена. Целей для калорийности и стоимости нет.

### 5.4. Временно отключённые продукты

Временное исключение хранится непосредственно в `RationEntry.enabled`. Значение `false` означает, что конкретная позиция остаётся в рационе, но не участвует в расчётах.

## 6. Хранение данных

### 6.1. Гостевой режим

Используется `localStorage`. Актуальные ключи:

| Ключ | Содержимое |
|---|---|
| `food-calc.products.v1` | полный каталог продуктов |
| `food-calc.ration-entries.v1` | позиции рациона, порядок, граммовки и `enabled` |
| `food-calc.targets.v1` | дневные цели БЖУ и клетчатки |

Старые ключи `food-calc.amounts.v1`, `food-calc.hidden-products.v1` и `food-calc.ration-order.v1` читаются только для миграции прежней модели. Если сохранённые данные невозможно прочитать, используется стартовое значение.

### 6.2. Авторизованный режим

Google-вход реализован через Firebase Authentication и `signInWithPopup`. Для вошедшего пользователя конфигурация хранится по пути:

```text
users/{uid}/state/current
```

Документ содержит `products`, `rationEntries`, `targets`, `schemaVersion`, целочисленную `revision`, `updatedBy` и серверное поле `updatedAt`. Старый документ без `revision` считается ревизией `0` и мигрирует при следующей записи.

Для каждого аккаунта в `localStorage` хранится отдельная копия `food-calc.user.{uid}.v2` с `baseRevision`, локальной ревизией и признаком `dirty`. Общий ключ `food-calc.device-id.v1` идентифицирует устройство. Отбрасываемая при разрешении конфликта версия сохраняется в `food-calc.conflict-backup.{uid}.v1`.

- Интерфейс всегда работает с локальным состоянием и не ждёт сеть.
- До определения пользователя и получения первой достоверной версии данных показывается экран загрузки; стартовая конфигурация в этот момент не отображается.
- Локальная запись откладывается на 250 мс, облачная — на 900 мс после последнего изменения.
- Облачная запись выполняется транзакцией: данные отправляются только если `baseRevision` совпадает с актуальной облачной ревизией.
- Если изменилась только одна сторона, она автоматически передаётся на другую.
- Если после общей ревизии изменились обе стороны, синхронизация приостанавливается до явного выбора пользователя.
- Можно выбрать данные устройства, данные из облака или отложить решение; до выбора ни одна версия не перезаписывается.
- Перед заменой сохраняется одна локальная резервная копия отбрасываемой версии.
- Без сети изменения остаются локально с `dirty: true` и повторно отправляются после восстановления подключения.
- При первом входе изменённые гостевые данные не затирают существующее облако: различающиеся версии требуют подтверждения.
- Перед выходом выполняется дополнительная попытка синхронизации, но ошибка сети не блокирует выход.
- После выхода приложение возвращается к отдельной гостевой конфигурации.

В настройках есть отдельная вкладка «Синхронизация» со статусом, временем последней успешной операции, ручной проверкой, разрешением конфликта и скачиванием последней конфликтной копии. Статусы также показываются в меню аккаунта.

## 7. Каталог и дневной рацион — разные сущности

Это принципиальное продуктовое решение.

- Создание нового продукта добавляет его только в каталог.
- В дневной рацион продукт добавляется отдельным действием из каталога.
- При добавлении в рацион начальная граммовка равна 100 г.
- Уже выбранный продукт помечается в каталоге как «В рационе».
- Удаление из дневного рациона не удаляет продукт из каталога.
- Удаление из каталога удаляет продукт также из дневного рациона и требует подтверждения.
- Редактирование характеристик продукта изменяет их и в каталоге, и во всех расчётах рациона, поскольку используется один и тот же объект продукта.
- Дубликаты названий технически разрешены.

## 8. Создание и редактирование продукта

Форма открывается в компактном модальном окне.

Обязательное поле:

- `name` — непустое название.

Необязательные числовые поля:

- белки;
- жиры;
- углеводы;
- клетчатка;
- калорийность;
- цена упаковки;
- вес упаковки.

Внутри формы числа временно хранятся строками. Это сделано, чтобы пользователь мог полностью очистить контролируемый input и спокойно ввести новое значение. При сохранении пустое или некорректное числовое значение безопасно преобразуется в `0`. Отрицательные значения также нормализуются до `0`.

## 9. Расчёты

Для продукта с дневным количеством `amount`:

```text
коэффициент = amount / 100
нутриент за день = значение на 100 г × коэффициент
цена за грамм = цена упаковки / вес упаковки
стоимость за день = цена за грамм × amount
```

Если вес упаковки равен нулю, стоимость продукта считается равной нулю — деления на ноль нет.

Итоги суммируются только по активным продуктам. Временно отключённые позиции полностью исключаются из БЖУ, клетчатки, калорий, дневной стоимости, месячной стоимости и прогресса целей.

Месячная стоимость сейчас рассчитывается как:

```text
стоимость дня × 30
```

Количество дней пока зафиксировано в `App.tsx` и не настраивается пользователем.

Числа и рубли форматируются для локали `ru-RU`.

## 10. Дневные цели

В сводке есть кнопка «Настроить цели». Настраиваются белки, жиры, углеводы и клетчатка в граммах на день.

Индикация:

- цель не задана — показывается «Цель не задана»;
- менее 80% — нейтральная шкала;
- от 80% до 99% — жёлтая шкала;
- 100% и более — зелёная шкала;
- визуальная полоса заполняется максимум до 100%;
- текстовый процент может быть больше 100%.

Кнопка «Сбросить цели» очищает поля формы; изменения применяются после сохранения.

## 11. Временное исключение продукта

В дневной таблице и мобильной карточке рядом с редактированием и удалением из рациона находится кнопка-глаз.

- Обычный глаз — продукт участвует в расчётах.
- Перечёркнутый глаз — продукт не участвует в расчётах.
- Отключённая позиция затемняется и получает отметку «Не учитывается».
- Отметка находится в одной строке с названием и не меняет высоту строки или карточки.
- Количество продукта сохраняется.
- Повторное нажатие возвращает позицию в расчёты.
- Состояние сохраняется между посещениями.
- Каталог продолжает считать такую позицию добавленной в рацион.

## 12. Импорт отдельных продуктов

В каталоге есть действие «Импорт JSON». Оно предназначено только для добавления продуктов в каталог, а не для восстановления всей конфигурации.

Поддерживаются одиночный объект и массив объектов:

```json
{
  "name": "Морковь",
  "protein": 1.3,
  "fat": 0.1,
  "carbs": 6.9,
  "fiber": 2.4,
  "calories": 35,
  "packagePrice": 70,
  "packageWeight": 1000
}
```

```json
[
  {
    "name": "Морковь",
    "protein": 1.3,
    "fat": 0.1,
    "carbs": 6.9,
    "fiber": 2.4,
    "calories": 35,
    "packagePrice": 70,
    "packageWeight": 1000
  }
]
```

Правила:

- обязательно только непустое строковое поле `name`;
- числовые поля должны быть конечными неотрицательными JSON-числами;
- отсутствующее поле, `null` или пустая строка преобразуются в `0`;
- неизвестные поля игнорируются;
- `id` из входных данных не используется, приложение создаёт новый;
- при любой ошибке не импортируется ничего;
- предпросмотра нет;
- дубликаты не проверяются и добавляются как отдельные продукты;
- импортированные продукты не добавляются в дневной рацион автоматически.

Сообщение об ошибке намеренно краткое: «Не удалось прочитать JSON. Проверьте формат и попробуйте ещё раз».

## 13. Markdown-экспорт активного рациона

Назначение — предоставить чистые структурированные данные о рационе человеку или чат-боту. Экспорт не содержит инструкций по анализу или готовых промптов.

В отчёт включаются:

- дневные итоги;
- вручную заданные цели;
- активные продукты;
- граммовка и рассчитанные показатели каждого продукта.

Не включаются:

- временно отключённые продукты;
- цены и стоимость;
- данные упаковки;
- внутренние ID;
- проценты выполнения целей;
- пояснения, советы и инструкции чат-боту.

Формат:

```markdown
# Типичный дневной рацион

## Итоги за день

| Показатель | Значение | Цель |
|---|---:|---:|
| Калорийность | 2130 ккал | — |
| Белки | 126,4 г | 140 г |
| Жиры | 68,2 г | 70 г |
| Углеводы | 241,5 г | 250 г |
| Клетчатка | 27,8 г | 30 г |

## Продукты

| Продукт | Количество | Ккал | Белки | Жиры | Углеводы | Клетчатка |
|---|---:|---:|---:|---:|---:|---:|
| Куриная грудка | 250 г | 283 | 59 г | 4,8 г | 0 г | 0 г |
```

Если цель не задана, используется `—`. Символ `|` и переносы строк в названии продукта экранируются. Интерфейс экспорта содержит read-only поле, ручное выделение и кнопку «Скопировать».

## 14. Интерфейс и адаптивность

На десктопе:

- сверху расположена сводка калорий, стоимости, БЖУ и клетчатки;
- ниже находится таблица дневного рациона;
- каталог, импорт, экспорт, редактирование и цели открываются в модальных окнах.

На экранах до 720 px:

- таблица скрывается;
- продукты отображаются отдельными карточками;
- количество управляется широким контролом с кнопками `−` и `+`;
- модальные окна открываются как нижние панели;
- управляющие кнопки перестраиваются под ширину экрана.

Используются собственные SVG-иконки без иконочной библиотеки. Предусмотрены доступные названия кнопок, `role="dialog"`, закрытие модальных окон по Escape и учёт `prefers-reduced-motion`.

## 15. Визуальные решения

- спокойная светлая палитра с зелёным основным цветом;
- карточки с тонкими границами и мягкими тенями;
- строки рациона подсвечиваются по наиболее значимому нутриенту: белок — красным, жир — жёлтым, углеводы — синим, клетчатка — зелёным;
- значимость БЖУ определяется долей от 250 ккал вклада нутриента, клетчатки — долей от 8 г в порции; интенсивность имеет фиксированную шкалу и ограничена 14% прозрачности;
- если второй нутриент набирает минимум 30% своей шкалы и не менее 65% значимости лидера, фон становится двухцветным градиентом; более слабые примеси не добавляют второй цвет;
- общие цвета, размеры, радиусы, тени и переходы вынесены в SCSS-переменные;
- интерфейс не зависит от внешних шрифтов и сетевых ресурсов.

## 16. Полный backup конфигурации

Экспорт всей конфигурации реализован в виде JSON-файла. Он не должен путаться с импортом отдельных продуктов или Markdown-отчётом. Восстановление из такого backup пока не реализовано.

Текущий формат:

```json
{
  "format": "food-calc-backup",
  "version": 2,
  "exportedAt": "2026-08-06T12:00:00.000Z",
  "settings": {
    "daysInMonth": 30
  },
  "targets": {
    "protein": 140,
    "fat": 70,
    "carbs": 250,
    "fiber": 30
  },
  "products": [
    {
      "id": "chicken",
      "name": "Куриная грудка",
      "protein": 23.6,
      "fat": 1.9,
      "carbs": 0,
      "fiber": 0,
      "calories": 113,
      "packagePrice": 349,
      "packageWeight": 700
    }
  ],
  "ration": [
    {
      "id": "entry-chicken",
      "productId": "chicken",
      "amount": 250,
      "enabled": true
    }
  ]
}
```

Семантика:

- экспорт включает каталог, рацион, порядок и ID позиций, граммовки, цели и состояние глазика;
- `enabled: false` соответствует временно отключённой позиции;
- из экспорта исключаются позиции рациона, ссылающиеся на отсутствующие продукты;
- `format` и `version` нужны для проверки совместимости.

При будущем добавлении восстановления текущая конфигурация должна заменяться только после полной валидации файла и явного подтверждения пользователя. При ошибке данные не должны меняться.

## 17. Осознанные ограничения текущей версии

- гостевые данные привязаны к конкретному браузеру и устройству;
- облачная синхронизация доступна только после входа через Google;
- нет истории изменений и автоматических снимков конфигурации;
- JSON-backup можно скачать, но пока нельзя восстановить через интерфейс;
- нет истории рационов по датам;
- поддерживается один типичный день;
- месяц всегда равен 30 дням;
- цели задаются вручную и не рассчитываются из пола, возраста, веса или активности;
- не учитываются витамины, минералы, сахар, соль и жирные кислоты;
- импорт продуктов не обновляет существующие позиции и не обрабатывает дубликаты;
- Markdown-экспорт предназначен только для передачи данных, а не для последующего восстановления состояния;
- автоматических тестов нет.

## 18. Инварианты для дальнейшей разработки

Следующим разработчикам и чат-ботам важно сохранять эти правила:

1. Каталог и дневной рацион не объединять обратно в один список.
2. Создание продукта не должно автоматически добавлять его в рацион.
3. Удаление из рациона не должно удалять продукт из каталога.
4. Пустые числовые поля должны оставаться редактируемыми и сохраняться как нули.
5. Временно отключённый продукт должен сохранять граммовку и членство в рационе.
6. Отключённые продукты не должны попадать ни в расчёты, ни в Markdown-отчёт.
7. Пользовательские цели не являются медицинскими нормами.
8. Markdown-отчёт должен оставаться чистым набором данных без промптов и рекомендаций.
9. Полный backup и импорт отдельных продуктов — разные форматы и разные действия.
10. Гостевой режим должен оставаться полноценным и сохранять данные локально без обязательного сервера.
11. При первом входе гостевая конфигурация переносится автоматически только при пустом облаке; различающиеся локальная и облачная версии требуют явного выбора.
12. Документы Firestore должны быть доступны только владельцу по его Firebase UID.
13. Облачную запись нельзя выполнять без проверки `baseRevision` в транзакции.
14. При конфликте ни локальная, ни облачная версия не должна перезаписываться автоматически.

## 19. Текущее состояние

Реализованы каталог, дневной рацион с повторяющимися позициями и ручной сортировкой, CRUD продуктов, JSON-импорт продуктов, локальный гостевой режим, расчёты, цели, временное исключение позиций, адаптивный интерфейс, Markdown-отчёт и скачивание полного JSON-backup версии 2.

Добавлены вход через Google и двусторонняя синхронизация каталога, рациона и целей через Cloud Firestore. Авторизованные данные имеют отдельную локальную копию, облачные записи защищены ревизиями и транзакциями, офлайн-изменения повторяются после подключения, а расхождение двух изменённых версий разрешается только после подтверждения пользователя. В настройках доступна отдельная вкладка синхронизации.

Правила Firestore находятся в `firestore.rules`; их необходимо опубликовать в Firebase-проекте. Production-сборку следует повторно проверять после изменений исходного кода и перед развёртыванием.
